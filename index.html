不能换马的驿站

西北有条走了几百年的驿道。驿道上有个死规矩：马是官马，一匹也不许换，连马吃的草料都不许动。

老周到最偏远的那座驿站当驿丞那年，正赶上驿道往外延伸：每个月都要派骑手去一条从没人走过的新路送信。路一条比一条怪，马还是那几匹马。前任驿丞跑得慢，被撤了，临走嘟囔了一句：“马就这样，有什么办法。”

老周不信这个邪。他围着马转了三天，在本子上列了张单子——马不能动，可马身上、马身边的东西，总能动吧？

他先改了骑手出发前要念的那段话：去哪、送什么、先走哪段后走哪段。又在几个出过事的路口挂上红布，红布底下写着“此处必须下马牵行”“此处绝不能抄近道”。他把历年骑手的心得抄成一本路书，只留每条路都用得上的那几条。岔路口立起木牌，写清哪条通水源、哪条通集镇。

有些本事不是每趟都用得上，比如怎么过流沙。老周把过流沙的法子写进一只锦囊，交代骑手：“看见流沙再拆。”货物要过秤，骑手以前全凭眼力估，老周就在鞍边挂了一杆秤和一把尺。要探路的时候，先放一匹小驹出去，它回来只带一句话：前面能不能走。

最后一样最费心思。有一段冰面，红布挂了，话也念了，骑手还是图快骑马冲过去，摔了两回。老周请铁匠在马蹄铁里装了个机关：一踩上冰，防滑钉自己弹出来。这一回，骑手想跳过也跳不过去。

当然也走过弯路。有一阵子路书越写越厚，骑手出发前光念就要念半个时辰，反倒误了行程，老周只好删掉一半。还有一只锦囊在箱底躺了半年，从没人拆过——没人知道有这只锦囊，有它和没它一个样。从那以后，老周每添一只锦囊，都要在红布上补一行：“遇到某某情况，拆某某锦囊。”

一年后，巡查的官员来了。驿站的马还是那几匹，新路上的信却快了一倍。官员绕着马看了半天，问：“你到底换了什么？”

老周拍了拍马背上那一整套家什，笑而不答。

谜底：Harness ——“马具”

英文 harness 的本义就是马具。在 AI 代理里，它指包在冻结的大模型外面、决定模型“怎么干活”的那一整套可编辑部件：提示词、护栏、记忆、工具说明、子代理、技能、脚本、插件。Harness² 不训练模型、不改一个权重，只改马具。

四种运行时角色：从“说”到“做”

项目 README 把八个组件按运行时角色分成四组。理解这四组的关键，是看它们离“模型自己决定”有多远：

角色组件怎么影响代理代价与力度
上下文构建C1 C2 C3 C6往模型的上下文里放文字最便宜；但模型可以“读了不照做”
工具接口C4 C7告诉它怎么用工具 / 给它确定性的新工具把容易算错的步骤交给代码
编排C5把一段活派给有独立上下文的子代理省主上下文，但多一次调用
中间件C8在工具循环内部拦截、改写唯一“模型跳不过”的杠杆；也最容易误伤
设计要点：用“最便宜的有效部件”项目给编辑器的提示词里反复强调：把每个失败对应到最便宜、但足够有效的部件。普通的先后顺序问题，写一句常驻提示就够；重复的机械劳动才写脚本；只有反复证明“写清楚了也会被跳过”的硬规矩，才动用插件。老周也是先挂红布，摔了两回才去改蹄铁。（第 3 站会细讲这套对应关系。）

在代码里，harness 就是一个字典

整个项目里，一棵 harness 的类型只有一行：

Tree = dict[str, str]   # 一棵 harness = {相对路径: 文件内容}，就这么简单

不同执行器（OpenCode、Codex）允许编辑哪些路径、有哪些限制，写在一个叫 SurfaceSpec（可编辑表面）的冻结数据类里。下面是默认执行器 OpenCode 的那一份：

OPENCODE_SURFACE = SurfaceSpec(
    name="opencode",
    always_on=(                                   # 常驻：每次调用都整段放进上下文
        "systemprompt.md",                        # C1 系统提示
        "guardrails.md",                          # C2 护栏
        "LongTermMEMORY.md",                      # C3 长期记忆
        "tool_descriptions/tool_guidance.md",     # C4 工具说明
    ),
    always_on_max=24_000,                         # 常驻内容合计上限（字符数）
    always_on_cap_reason="every token here competes with the agent's own output budget",
    skill_dir="skills",                           # C6 技能：skills/<名>/SKILL.md
    skill_name_rule="must_match",                 # frontmatter 的 name 必须等于目录名
    autotrigger_file="guardrails.md",             # 自动补触发行时写进这个文件
    trigger_line="- When {desc}, load the `{name}` skill.\n",
    subagent_requires_mode=True,                  # C5 子代理必须声明 mode: subagent
    plugin_dir="plugin",                          # C8 插件：plugin/<名>.ts
    hooks_file=None,                              # OpenCode 没有 hooks 文件
    # ……其余字段省略
)

上限的理由写得很直白：“这里的每一个 token，都在和代理自己的输出预算竞争”——就是老周那本越写越厚的路书。

本站带走三句话
  • Harness = 冻结模型之外一切可编辑的部件；Harness² 只改它，不改权重。
  • 八个组件分四种角色；越靠近“机制”越难被跳过，也越贵、越容易误伤——优先用最便宜的有效部件。
  • 代码里一棵 harness 就是 dict[str, str]；每个执行器的规矩写在一份 SurfaceSpec 里。

没有考官的厨房

老秦的小馆有条怪规矩：每天只接一位客人，客人点的一定是店里从没做过的菜，要求只有一两句话。没有美食评论家，没有标准菜谱，客人吃完就走，从不打分。

掌勺的还是那位厨子，手艺改不了。老秦能改的，只有挂在灶台边那一叠“做菜规矩”。

新菜来了，老秦不急着改规矩。他先让厨子照老规矩做两锅，自己站在边上看——不尝味道，只记过程：几时下油、几时翻锅、哪一步手忙脚乱。两锅都在同一步粘了锅。老秦在本子上写：“两锅都粘，是规矩的毛病。”有一锅盐放多了，他想了想，没写：“一锅的事，兴许是手抖。为它改规矩，是冤枉规矩。”

合成是整个方法里最需要判断力的一步。项目给合成器的提示词（prompts.aggregate）开宗明义：你交出的东西就是被采纳的东西……你是最后一道关，合并一条改动就等于替它“洗白”（you are the last gate, and merging an edit launders it）。下面是它的称重规则：

规则（中文意译）原文要点
k 次基础执行来自同一个分布，要当成一组看，而不是 k 个独立故事draws from ONE distribution -- read them as a set

每个候选只跑了一次，单次好坏都是弱证据；改动要靠轨迹里某个具体时刻显示出作用机制才算数'this looks like good practice' is not evidence; name the moment.
下行风险和上行收益同等看重；关联执行什么都没交付的改动，视为不安全treat that edit as UNSAFE
候选之间意见一致，只是支持，不是独立证明（它们共享任务、证据和模型偏见）；意见矛盾就去读轨迹，而不是投票Agreement is support, not independent proof; contradiction is a reason to inspect the trajectories, not to vote.
三种都是合法结果：跨候选合并（INV 和 DOM 各有贡献时最常见）、整版采纳一个、保持原样MERGE / ADOPT ONE WHOLESALE / KEEP_BASE

为什么要“蒙眼”？

选择器也是一个大模型。如果它看得到“这是改了 5 个组件、加了 3 个技能的版本”，就很容易偏向看起来更用心的那个。所以 Harness² 在设计上把过程信息全部拿掉：

  • 匿名：只有字母，没有 agg2、c3 这种暴露来源和轮次的标签。
  • 打乱：字母顺序和生成顺序无关，避免“最后一个最好”之类的位置偏见。
  • 只比交付物：harness、轨迹都不给看。
  • 可复现：种子由任务、k、模式决定，重跑同一配置，字母分配完全一样，方便审计和断点续跑。
def assign_ids(labels, *, task_id, k, mode) -> dict[str, str]:
    """匿名 id -> 标签：先按规范顺序排序，再用固定种子打乱——重跑结果稳定。"""
    seed = int(hashlib.sha1(f"{task_id}|{k}|{mode}".encode()).hexdigest()[:12], 16)
    ordered = sorted(labels)                 # 先排序：与传入顺序无关
    random.Random(seed).shuffle(ordered)     # 再用独立的随机数生成器打乱，不影响全局随机状态
    return {_anon_id(i): lbl for i, lbl in enumerate(ordered)}   # A, B, C, …, Z, AA, AB …

def selection_pool(mode, k, rollouts, base):
    """选择池只有一个出处：恰好是该模式的 k 个最终候选。"""
    del base          # 参数故意不用：传进来是为了在调用处“看得见”基础执行被排除了
    labels = ([f"agg{i}" for i in range(1, int(k) + 1)] if mode == "agg"
              else [f"c{t}" for t in range(1, int(k) + 1)])
    return {lbl: rollouts[lbl] for lbl in labels if lbl in rollouts}

注意 del base 这个小设计：参数明明不用，却要求调用方传进来。注释解释说，这样“排除基础执行”这件事在构建池子的地方一眼就能看见，不会被误以为是遗漏。

谜底：反思 + 经验库 —— 第二层“改进级递归”

每个任务选定交付后，Harness² 再开一次反思会话（reflect_adoption），逐条评估每处改动，最多提炼一条可迁移的经验；然后把被采纳的整棵 harness 连同经验存进按领域划分的经验库（Library）。同领域后面的任务在提议时都能读到它。经验库就是项目所说的改进 harness（improvement harness）：它不给干活的代理用，而是给“改马具的人”用——改进过程本身也在被改进，这就是第二层递归。

反思会话的三条原则

① 被采纳的候选不是唯一的证据“Selection compared DELIVERABLES with the harnesses hidden, so the choice says which output read best -- not which edit worked. … Read the trajectories, not the verdict.”
盲选只说明哪个产出读起来最好，不说明哪条改动起了作用。只出现在落选候选里的改动，可能才是真正改善行为的那一条。
② 宁可写“说不清”，也不编因果一个候选同时改了好几个组件、没有哪次执行能单独隔离其中一个，或者差异只靠一次执行撑着——都应该用 confounded，而且优先用它。原文：“A confounded row is a useful record; an invented attribution poisons the library for every later task.”
③ 经验要“刚好”能迁移cue 描述的是局面的形状，不是这个任务的事实；lesson 是对 harness 的一个可执行、可检查的操作，必须点名组件。太空泛没用（“be thorough”），太具体不会再触发（“the fee rose to 250 on Jan 1”）；刚好的例子：“当一份文书包含几个先后生效的行为、其中一个会终止行为人自己的权限时，把终止权限的那个放在最后”。只靠 confounded 行撑着的经验是猜测，要么收窄，要么放弃。

刻进石碑的章程

行会的章程原先写在纸上，挂在各分号的墙上。纸上的字谁都能用铅笔改两笔。有一年，南边分号把“学徒期三年”悄悄改成了“两年”，北边分号不知道，两边带出来的学徒一碰面，差点打起来。更糟的是，没人说得清是哪天、谁改的。

新任会首定了新规矩：章程刻在石碑上。

刻碑之前，石匠要拿着行会的根本法，把每一条逐字核对：有没有写错的名目、有没有低于底线的数字、该指定的见证人有没有指定。有一条不合，整块碑就不刻。“宁可当场刻不成，也别刻好了立在那里，三个月后才发现是错的。”

碑一旦刻成，谁也改不了一个字。真要改，就另刻一块新碑：没变的条文照抄，变的那条换掉——新碑刻之前，照样要逐条核对。

有几条是捆在一起的。比如“走哪条驿路”和“派哪位信使”：“只换路不换人，或者只换人不换路，信都会送丢。要换，两条一起换。”

当然，不是什么都刻石头。每天的流水账、谁今天出了几趟工，还是记在纸本子上，随时往上添。会首说：“章程刻石，账本用纸。一块碑说的是‘这件事是什么’，不是‘这件事怎么干’。”

猜一猜：“刻进石碑、刻前逐条核对、要改就另刻一块”，对应 Python 里的哪种写法？

谜底：@dataclass(frozen=True) + __post_init__ 校验 + dataclasses.replace

Harness² 的所有配置类（SurfaceSpec、ChannelSpec、BenchPrompts、BenchSpec、Namespace 等）都是冻结的数据类：创建后不能修改；创建时在 __post_init__ 里把所有约束检查一遍，不合法当场报错；需要变体时用 replace() 生成一个新值——新值同样要过校验。而记录运行过程的类（RunView、Stage、Ledger、Selection）是普通可变数据类。

生意大了，掌柜添了马：驿站只有两匹快马，所以最多同时派两个信使。新问题马上来了——信使谁先回来全看路况，今天东镇的先回，明天北镇的先回。账房如果照“回来的先后”记账，同样的四单生意，每天记出来的顺序都不一样，月底对账的人头都大了。

老账房想了个办法：“回来一个，我先把回执收进抽屉，不动账本。等今天的信使全部回齐，再照着派单簿上的顺序一笔笔誊进去。这样不管派一个还是派两个，账本读起来一模一样。”

后来又出过两回事。一回是暴雨，四个信使只回来两个，第二天掌柜又让把四单全部重送一遍，白白多花了两份脚钱。另一回，有个信使在货栈门口看到一箱货，以为就是自己的，空手回来报“送到了”——其实那是上个月另一个版本的货单剩下的。

老账房于是立了三条规矩：

第一，“货在仓里，不算送到。”只有信使亲手交回、盖了火漆的回执才算数；回执上还要印着这一版货单的指纹。货单哪怕改了一个字，旧回执就作废。

第二，写回执先写在草稿纸上，写完了一把换进回执匣。谁也不会在匣子里看到一张写了一半的回执。

第三，“断了就照原样再派一次。”第二天把同一张派单簿再执行一遍：有合格回执的那几单直接跳过，没回执的、或者回执指纹对不上的，才重新派人。

还有一个小细节：每个信使出门前，都拿到一份货单的誊抄本，原件锁在柜里，谁也带不走、改不着。每一单还有个独一无二的编号，写明“哪个商号、哪个分号、第几批、哪一单”——“分号的名字不能空着，空着的话，东西两个分号的回执就要混在一起了。”

猜一猜：“同时派人但照派单簿记账”“盖指纹的回执”“断了照原样再派一次”，合起来是哪一类工程设计？

谜底：并发但结果有序 + 幂等的断点续跑

Harness² 的各个阶段用 ThreadPoolExecutor 并发执行（宽度 PHASE_WIDTH = 2），但账本永远在线程池收尾之后、按调用方给定的顺序写入，所以并发运行和串行运行记下的标签序列完全相同。每次 rollout 成功返回后写一个 .adapt_complete 完成标记（原子写入、带马具指纹）；重跑同一条命令时，只有“标记有效且指纹一致”的结果才会被复用——这让整条流水线可以随时中断、原样重跑。

def _roll_many(adapter, ledger, task_id, items, run_id_of, work_dir, *, width) -> dict[str, RunView]:
    """Roll independent harnesses concurrently, then record them in the caller's order.

    The ledger is written after the pool drains, so a concurrent run records the same sequence
    of labels as a serial one.
    """
    # 中文：并发执行互不依赖的马具，再按调用方给的顺序记账。
    #       账本在线程池清空之后才写，所以并发运行和串行运行记下的标签序列一模一样。
    out: dict[str, RunView] = {}
    if not items:
        return out
    n = max(1, min(len(items), width))
    if n == 1:                                   # 宽度为 1：就是普通串行，边跑边记
        for label, tree in items:
            out[label] = _roll(adapter, ledger, task_id, label, tree, run_id_of, work_dir, record=True)
        return out
    with ThreadPoolExecutor(max_workers=n) as pool:
        got = list(
            pool.map(                            # ① map 的结果顺序 = 输入顺序，与谁先跑完无关
                lambda it: _roll(adapter, ledger, task_id, it[0], it[1], run_id_of, work_dir,
                                 record=False),  # ② 线程里不碰账本
                items,
            )
        )
    for (label, _tree), rv in zip(items, got):   # ③ with 块结束 = 所有线程已收工
        ledger.rollout(label)                    # ④ 再按派单顺序一笔笔记
        out[label] = rv
    return out
为什么不直接在线程里 ledger.rollout()？在 CPython 里 list.append 本身不会把列表写坏，但顺序取决于谁先跑完，每次都可能不同。账本的顺序会进入 summary.json 和报表，第 6 站的 assert_identity 也要逐条核对它。让顺序“确定”，同一份配置跑两遍才能逐字节比较。另外，_roll 自己把异常转成一条 ok=False 的记录（“A dead rollout is recorded, never raised.”），所以一个线程出错不会让 pool.map 半路抛异常、把其他结果丢掉。

import random, time
from concurrent.futures import ThreadPoolExecutor, as_completed

def 送信(镇子):
    time.sleep(random.random() / 10)     # 路况随机
    return 镇子

派单簿 = ["东镇", "西镇", "南镇", "北镇"]
with ThreadPoolExecutor(max_workers=2) as pool:
    print(list(pool.map(送信, 派单簿)))  # 永远是 ['东镇', '西镇', '南镇', '北镇']

with ThreadPoolExecutor(max_workers=2) as pool:
    futs = [pool.submit(送信, z) for z in 派单簿]
    print([f.result() for f in as_completed(futs)])  # 谁先完成谁在前：每次可能不同

pool.map 按输入顺序交还结果，适合“结果要按固定顺序处理”；as_completed 按完成顺序交还，适合“先完成的先处理”。Harness² 在需要确定顺序的地方（rollout、提议会话）用前者；评审器 judge.py 给一批选中结果打分时用后者——每条分数记录自带任务名、模式和标签，谁先出来都不影响后续统计。

"""Trial identity: was this rollout finished, and by this configuration?

Completion is recorded explicitly by the code that observed the run return; presence of output
is not enough. The marker also fingerprints the harness that produced the rollout, so a rollout
from a different configuration is never reused.

#       完成与否，由亲眼看到运行正常返回的那段代码明确记下；目录里“有输出”不算数。

    return h.hexdigest()[:16]            # （__pycache__、.pyc、.DS_Store 不参与）

def mark_complete(where, *, run_id, harness_dir=None, extra=None):
    """Record that `run_id` finished. Call only after the runner returned normally."""
    payload = {"version": VERSION, "run_id": run_id, "at": time.time(),
               "harness": fingerprint(harness_dir), **(extra or {})}
    tmp = d / f"{MARK}.{os.getpid()}.tmp"
    tmp.write_text(json.dumps(payload, indent=2, sort_keys=True))   # ① 先写草稿
    os.replace(tmp, d / MARK)                                       # ② 原子替换：要么旧的，要么完整的新的

def is_complete(where, *, harness_dir=None, match_harness=True) -> bool:
    m = read_mark(where)
    if not m or m.get("version") != VERSION:
        return False
    if not match_harness:
        return True
    return m.get("harness") == fingerprint(harness_dir)            # ③ 指纹必须一致

def ns(benchmark, substrate, mode, k, *, seed=None, tag="") -> str:
    if mode not in MODES:
        raise ValueError(f"unknown mode {mode!r}; the method has exactly two: {MODES}")
    if not substrate:
        raise ValueError("namespace needs a substrate name ('oc' | 'cx'); an empty one would "
                         "let the two substrates' caches collide on every label")
        # 中文：基底名不能为空，否则两个基底的缓存会在每个标签上撞车
    out = f"{benchmark}-{substrate}-{mode}{int(k)}"     # 例：lab-oc-agg2
    if seed is not None: out += f"-s{int(seed)}"        # 例：lab-oc-agg2-s7
    if tag:              out += f"-{tag}"
    return out

@dataclass(frozen=True)                                 # 第 11 站：名字也是冻结的值
class Namespace:
    benchmark: str; substrate: str; mode: str; k: int; seed: int | None = None; tag: str = ""
    def run_id(self, task_id, label):
        return f"{self}/{task_id}/{label}"              # 例：demo-oc-agg2/ledger-1/inv1

因为每个 rollout 的名字精确到“基准-基底-模式-k-种子-标签/任务/候选”，缓存和完成标记都挂在这个名字下面，不同实验之间不会互相“捡到”对方的结果。注意基础 rollout（base1…basek）用的是一个共享的命名空间：两种模式共用同一批基础执行，既省钱，又保证两种模式从同一份证据出发、对比公平。

设计要点：确定性是“可续跑、可复现”的前提研究代码最怕两件事：中途崩了只能从头来；同一份配置跑两次结果对不上，说不清是方法的波动还是代码的波动。Harness² 的做法是：并发只用来省时间，不允许改变任何可观察的顺序；复用只认明确的完成标记 + 指纹；所有写入都“先写临时文件再原子替换”。于是“中断后重跑同一条命令”就成了一个安全、便宜、可重复的操作——这正是工程上说的幂等。

建议打开 library/k2/agg/accounting/harnesses/ledger-1/EXPERIENCE.md 看看：它记录了被采纳的是 agg1、为什么选它（“The signed total matches the source ledger.”）、每处改动的结论（verdict: helped）和一条可迁移经验。demo.json 里 ledger-2 的 library_entries_before 是 1——第二个任务开始前，经验库里已经有了第一个任务留下的那一条。

四、跑一个真实基准（会产生模型费用）

真实基准还需要 Node.js 20+、Google Cloud CLI 以及各基准自己的依赖（LAB 需要 Pandoc 和 Poppler，WorkBuddy-Bench 需要 Docker），并在 .env 里配置 Vertex AI 项目和模型。官方示例：

cp .env.example .env                 # 填写模型配置
gcloud auth application-default login

harness2-setup lab                   # 安装 LAB（法律工作）基准
harness2-check --bench lab           # 体检：依赖、凭据、数据是否齐全
harness2 --bench lab --k 1 --mode parallel \
  --only-domains antitrust-competition --max-tasks 1   # 只跑 1 个任务，先试水
harness2-judge --bench lab --k 1 --mode parallel       # 评审（只有这一步会用到评分标准，第 7 站）
harness2-report --bench lab --k 1 --mode parallel      # 出报表

# 常用变体
harness2 --bench lab --k 2 --mode sequential ...       # 串行递归（第 6 站）
harness2 --bench lab --k 1 --mode parallel --dry-run   # 只预览会选中哪些任务，不调用模型（第 11 站）
harness2 --bench lab --k 1 --mode parallel --substrate cx   # 换成 Codex 执行器（第 10 站）

三个基准：jb（JobBench，职业工作）、lab（LAB，法律工作）、wb（WorkBuddy-Bench，办公 / 网页 / 代码，后续命令都要带 --subset office|web|code）。评审和报表必须用和精修运行相同的基准、执行器、子集、--k、--mode 与种子。中断了就重跑同一条命令；换模型或换任务选择时，用一个新的 HARNESS2_RUNS_DIR。

务必先限制网络官方 README 特别提醒：执行器的网络访问不受限制，Codex 运行时还关闭了沙箱，而公开基准的评分细则可能在网上找得到。正式评测前，请按官方 docs/EXPERIMENTS.md#web-access 配置网络限制，防止执行器查到答案或评分标准——这是第 7 站“无答案原则”在运行环境上的延伸。

七、总测验

1. Harness² 改进智能体的方式是？
B。“不换马，换马具”，而且是两级递归：任务内（提议—试探—合成）+ 跨任务（经验库）。D 恰恰是第 7 站严格禁止的。
2. 在本地演示里，盲选为什么能选中正确的候选？
D。选择器看到的只有匿名字母、交付物和任务输入（source/）；它不知道哪个字母是哪个标签，也碰不到答案文件。
3. k=2 的并行模式里，下面哪一组标签恰好构成账本里的全部 rollout？
A。R = 4k = 8：k 个基础 + 2k 个候选 + k 个合成。顺序也固定如此（第 12 站）。
4. 编辑器交回的马具里新增了一个 notes.txt，会怎样？
C。这是第 8 站的“校验—回灌—重试”：不在可编辑面里的路径不被接受，失败也不会让流水线崩溃。
5. 想给 Harness² 接一个新的基准，最少需要做什么？
B。三轴解耦 + 结构化类型（第 10 站）：核心代码不认识任何具体基准；本地演示的 DemoAdapter 就是最好的范本。
最后，把全景图再看一遍回到序章的架构图，从红色主干开始，试着不看文字，把每个方框用一句话讲出来：马具是什么（1）→ 一步递归怎么走（2）→ 往哪两个方向提议（3）→ 怎么公平地挑（4）→ 挑完怎么传承（5）；然后是让它“可信”的约束（6 预算、7 无答案、8 校验、9 证据边界），以及让它“能跑很久”的地基（10 解耦、11 冻结配置、12 并发与续跑）。能讲出来，这个项目你就真的懂了。
