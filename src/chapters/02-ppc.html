没有考官的厨房

老秦的小馆有条怪规矩：每天只接一位客人，客人点的一定是店里从没做过的菜，要求只有一两句话。没有美食评论家，没有标准菜谱，客人吃完就走，从不打分。

掌勺的还是那位厨子，手艺改不了。老秦能改的，只有挂在灶台边那一叠“做菜规矩”。

新菜来了，老秦不急着改规矩。他先让厨子照老规矩做两锅，自己站在边上看——不尝味道，只记过程：几时下油、几时翻锅、哪一步手忙脚乱。两锅都在同一步粘了锅。老秦在本子上写：“两锅都粘，是规矩的毛病。”有一锅盐放多了，他想了想，没写：“一锅的事，兴许是手抖。为它改规矩，是冤枉规矩。”

接着，他叫来两个徒弟，让他们对着这两锅的记录，各自提一版新规矩。大徒弟盯的是“手上怎么做”，二徒弟盯的是“这道菜在行家眼里该是什么样”。

“光说不算数。”老秦让厨子照每一版新规矩真做一锅。

四锅做完，老秦把四份过程记录摊在桌上对照。大徒弟那版写了“油热后先离火三秒再下料”，那一锅在老地方果然没粘——这条留下，旁边注明：“老规矩两锅都在这一步粘锅，新规矩这锅在这一步没粘。”二徒弟那版添了一勺糖，可那一锅从头到尾看不出糖起了什么作用——删掉。还有一条“收汁要收到挂勺”，照着做的那锅直接烧糊，什么也没端出来——“端不出菜的改法，说得再好听也不能要。”

最后老秦只合成了一版规矩，挂回灶台。

徒弟问：“师父，要是哪一版都不比老规矩强呢？”老秦说：“那就留着老规矩，这也是答案。白加的规矩，占地方，还碍事。”

徒弟又问：“没人打分，您怎么知道哪条改对了？”老秦敲了敲那叠记录：

“每一处改动，都要指得出是哪一锅、哪一刻。指不出来的，就是猜。”

猜一猜：老秦这套“先照常做几锅 → 各提一版改法 → 每版真做一锅 → 对照过程合成一版”的功夫，在 Harness² 里叫什么？

谜底：提议—试探—合成（Propose–Probe–Compose）

这是 Harness² 任务级递归的一步：提议（Propose）几版 harness 修改 → 每版在同一个任务上真跑一次做试探（Probe）→ 根据执行之间的行为对比，合成（Compose）出一版最终 harness。全程没有标准答案、没有评分——信号只来自“同一个任务，不同 harness，过程有什么不同”。

三个动作，各管什么

提议 Propose编辑器读基础执行的证据，直接改一份 harness 副本。并行模式一次出 2k 版（k 个 INV + k 个 DOM）。
→
试探 Probe每个候选 harness 在同一个任务上真跑一次，得到它自己的轨迹和交付物。
→
合成 Compose合成器同时看基础执行和所有候选的执行，合并、整版采纳或保持原样，交出一棵树。

注意“试探”这一步的意义：编辑器提出的每条改动只是一个假设；只有真跑一次，才能在轨迹里看到它有没有改变行为。合成器做决定靠的就是这些行为对比，而不是改动“听起来多有道理”。

代码里：每一次“提议”或“合成”都走同一条流程

合成器手里的“称重规则”

合成是整个方法里最需要判断力的一步。项目给合成器的提示词（prompts.aggregate）开宗明义：你交出的东西就是被采纳的东西……你是最后一道关，合并一条改动就等于替它“洗白”（you are the last gate, and merging an edit launders it）。下面是它的称重规则：

规则（中文意译）原文要点
k 次基础执行来自同一个分布，要当成一组看，而不是 k 个独立故事draws from ONE distribution -- read them as a set
在基础执行里反复出现的失败是真问题，是最有力的依据；只出现 1/k 次的是噪声，针对它改就是对单个样本过拟合A defect in 1/k is noise, and an edit aimed at it is overfitting to one sample.
每个候选只跑了一次，单次好坏都是弱证据；改动要靠轨迹里某个具体时刻显示出作用机制才算数'this looks like good practice' is not evidence; name the moment.
下行风险和上行收益同等看重；关联执行什么都没交付的改动，视为不安全treat that edit as UNSAFE
候选之间意见一致，只是支持，不是独立证明（它们共享任务、证据和模型偏见）；意见矛盾就去读轨迹，而不是投票Agreement is support, not independent proof; contradiction is a reason to inspect the trajectories, not to vote.
三种都是合法结果：跨候选合并（INV 和 DOM 各有贡献时最常见）、整版采纳一个、保持原样MERGE / ADOPT ONE WHOLESALE / KEEP_BASE

每条决定都要按固定格式写进 <notes>，例如：

kept    -> inv1: 写完后重新打开文件核对   -> failed in 2/3 base rollouts；inv1 在第 41 步重开文件并修正错列
dropped -> dom2: “保持专业、认真负责”       -> 与基础执行相比没有任何可观察的行为差异
dropped -> dom1: 收汁式的强制格式检查       -> dom1 的执行什么都没交付，UNSAFE

（上面三行是本教程编的示例，格式与提示词要求一致：kept|revised|dropped -> 哪条改动 -> 决定它的轨迹时刻或基础执行规律，涉及集合时写出计数。提示词的解释是：“A decision without evidence attached is a decision the next reader cannot audit.”）

你来当合成器：这条理由站得住吗？
k=3 时，有个缺陷只在 1 次基础执行里出现。为什么合成器不该专门为它改 harness？
B。就像老秦说的“一锅的事，兴许是手抖”。反复出现的失败才是 harness 的真实属性，也是最值得动手的依据。
本站带走三句话
  • 提议—试探—合成：改动先是假设，真跑一次才有证据，合成只认行为对比。
  • 所有改进会话都走 _run_stage：搭证据 → 开会话 → 收文件 → 校验 → 失败带着错误原文重试一次 → 再失败退回保底树。
  • “保持原样”是正经答案；每条决定都要指得出“哪一锅、哪一刻”。
