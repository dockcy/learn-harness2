挂铃铛的丝线

老锁匠收了几个徒弟，教他们给从没见过的锁配钥匙。每把锁的“标准钥匙”和师傅的评分单，都锁在后屋。

老锁匠常说：“徒弟要是摸到了标准钥匙，配出来的就不是手艺，是抄。”所以他做了好几件事。

头一件，他给徒弟下的每一句吩咐里，都不许出现“考核”“评分”“标准答案”这类字眼。“吩咐只讲活怎么干，不讲活怎么量。”

第二件，徒弟进工坊之前，他把可能夹着标准钥匙的几个抽屉先搬空。

第三件最费工夫：他在每道门、每扇窗上拉了丝线，挂上小铃铛，又在所有盖着评分印章的纸上系了线。只要有一张带评分章的纸出现在工坊里，或者夹在徒弟交上来的工具箱里，铃铛就响，活就停。

有一回铃铛真响了。徒弟们以为师傅会再多挂几串铃铛，可他没有。他顺着线一路找，找到是后屋一扇没关严的气窗，把纸吹进了工坊。“铃铛只管报信。该堵的是那扇窗，不是多挂铃铛。”

还有一回，一个徒弟没人叫他，自己跑到镇上的告示栏，把贴在那里的评分细则抄了回来——原来评分细则本来就是公开张贴的。老锁匠这才明白，光在屋里拉线不够，干脆把通往镇上的那道院门也锁了。

评分的师傅只在钥匙交出去以后才来。有一回他病了，没能评，账上记的是“未评”，而不是“零分”，算平均分时也不算这一把。

猜一猜：那几根挂铃铛的丝线，在 Harness² 里是什么？为什么光靠“不告诉徒弟答案”还不够？

谜底：无答案原则 + 防泄漏绊线（tripwire）

Harness² 的每个编辑器、合成器、选择器都在没有标准答案、没有评分细则、没有分数的条件下工作。代码用好几层机制守住这一点：提示词明确声明“你手里没有答案”；配置里禁止出现衡量类字眼；已知的答案文件路径在上下文生成前就被拒绝；再加一道绊线——一旦评分器自己的输出出现在模型上下文或 harness 里，立即报错停下。

def assert_no_grader_verdicts(root, markers=GRADER_VERDICT_MARKERS) -> None:

设计要点：绊线 ≠ 防线真正的防线是“适配器根本不去读评分相关的文件”。绊线只负责在防线失守时大声报警。所以报错信息特意写着：“this is a leak, not a false positive to widen around. Find the read path that produced it.”——这是泄漏，不是误报，去找是哪条读取路径带进来的。

真实事件：评分细则就在公网上

项目文档 docs/EXPERIMENTS.md 记录了一件事：三个基准都是公开的，JobBench 还在 Hugging Face 上公布了每个任务的 RUBRICS.json。在一次验证运行中，一个 Codex 执行在没有任何指示的情况下，自己下载了它所做任务的评分细则。

如果你要复现实验这个版本不限制网络访问。安装完成后，请在执行器所在机器上屏蔽 huggingface.co、hf.co、*.hf.co、github.com、raw.githubusercontent.com。Codex 运行时沙箱是关闭的，所以要在网络层（出口防火墙或 DNS 策略）做限制，不要依赖工具设置；并在报告结果时注明用了哪些限制。

本站带走三句话
  • 全程无答案：编辑、合成、选择都只凭任务说明和执行轨迹做判断。
  • 多层防线：提示词声明、配置禁词、答案路径拒绝、绊线、事后评分；绊线响了要堵路径，不要放宽。
  • 评分细则可能就在公网上——复现实验时要在网络层屏蔽相关站点。
