只标改动的裁缝

城里有家改衣铺，衣服由跑腿的送来，改好再由跑腿的送回去。

铺子的规矩是：小裁缝直接在原衣服上改。没动的针脚，原样保留；不许为了“保持原样”把整件拆了重缝一遍；要去掉一个口袋，就把口袋拆下来。“客人要的尺寸和样式，一分都不能动——你能改的是穿着舒不舒服，不是衣服的模样。”

改完不能直接送走。老师傅会拿着一张单子逐条验：领口的绣花加起来不能太重，否则穿的人抬不起头；每个暗袋都得缝上标签，标签上的名字要和口袋对得上，领口还得绣一行小字告诉穿的人“遇到什么情况，掏哪个暗袋”——“没人知道的暗袋，就是白添的分量。”口袋里的纸条写着“用口袋里的小剪刀”，那剪刀就必须真在口袋里；拉链要真能拉得动。缝到衣服外面去的东西，比如缝在跑腿的包上的，一律不算数。

有时候暗袋没绣提示，老师傅会顺手在领口补一行；可领口要是已经绣满了，他也补不了。

验不过，老师傅不会只说一句“不行”。他把所有问题一条一条抄在一张纸条上，原话照抄，和衣服一起退回去：“上次退回的原因如下，改好再交。”小裁缝只有一次返工机会。再验不过，客人就拿回原来那件衣服。

也有小裁缝看了半天，一针没动，附了张字条：“这件不需要改。”老师傅照样收下——“不该改的不改，也是手艺。”

猜一猜：这家铺子的“直接在原件上改、没动的原样保留、交货前逐条验、退回时附原话”，对应 Harness² 的哪套机制？

谜底：编辑契约 + 校验—回灌—重试

编辑器直接在 harness 副本上改文件：磁盘上的改动就是提议，没碰的文件原样继承。交回后，代码先自动补触发行，再跑三道校验（表面规则、基准规则、评分绊线）。不通过就把全部错误原文回灌给编辑器，重试一次；还不行就退回保底树。

注意两个“静默”：技能缺 description 或名字不符，执行器在加载时会悄无声息地丢掉它——不报错、不提示。Harness² 的校验器把这些“静默失败”提前变成响亮的错误，这是整个校验设计的出发点。

def validate(surface, tree, *, allow_subagents=True, always_on_max=None, reserved_scripts=...) -> dict:
    """抛出 ValueError，列出【每一个】问题；通过则返回这棵树的统计。"""
    errs: list[str] = []
    body = always_on_text(surface, tree)
    if len(body) > cap:
        errs.append(f"always-on content is {len(body)} chars, over the {cap} cap; "
                    f"{surface.always_on_cap_reason}")
    skills = _check_skills(surface, tree, body, errs)        # description / name / 是否被点名
    subs = _check_subagents(surface, tree, allow_subagents, errs)
    for rel, src in tree.items():                            # 脚本必须能编译
        if r["script"].fullmatch(rel) ...:
            _py_compiles(rel, src, errs)
    _check_script_refs(surface, tree, r, reserved_scripts, errs)   # 提到的脚本必须存在
    if errs:
        raise ValueError(" | ".join(errs))                   # 不是遇错即停，而是攒齐一次报完

def autotrigger(surface, tree, *, always_on_max=None) -> list[str]:
    """给每个技能在常驻文字里补一行触发；返回修好的技能名。
    如果补这一行会超出常驻上限，就跳过。"""
    for name in skill_names(surface, tree):
        if name in body:
            continue                                         # 已被点名
        ...
        line = surface.trigger_line.format(name=name, desc=desc)
        if len(always_on_text(surface, tree)) + len(line) + 2 > cap:
            continue                                         # 领口绣满了：补不了，留给 validate 报错
        tree[surface.autotrigger_file] = ... + line
设计要点：错误信息是写给模型看的适配器接口里 validate_tree 的文档写着：“Raise ValueError listing all problems in actionable prose: the message is fed back verbatim as retry feedback.” 所以每条报错都写成可执行的修改建议（比如“去掉 name: 行，或改成 name: x”），而且一次列出全部问题——编辑器只有一次返工机会，不能让它改了一个又撞上下一个。
先修再验_accept_tree 的顺序是：先 autotrigger（能自动修的先修掉），再 diff 判断是否原样保留，最后依次跑 tree.validate → adapter.validate_tree（基准自己的规则）→ assert_tree_has_no_grader_verdicts（第 7 站的绊线）。能机械修好的不浪费一次重试。
校验器操练场：选一个预设或直接改文件，看看能不能过
编辑器新增了 skills/doc_review/SKILL.md（有 name 和 description），但常驻文字里没提到它，而且常驻内容只差 10 个字符就到上限。会发生什么？
B。自动补触发行会检查上限，放不下就跳过；随后校验器发现技能没被点名，报错并给出修法：在 systemprompt.md 或 guardrails.md 加一行 “When <情况>, load the `doc_review` skill.”。编辑器重试时需要自己删减常驻内容腾出位置。
本站带走三句话
  • 编辑契约：原地改、没碰的继承、删文件即删组件；只改怎么做，不改交付物的形状。
  • 先自动修（补触发行），再三道校验；所有错误攒齐、原文回灌，只重试一次。
  • 校验的核心价值是把执行器的“静默丢弃”变成响亮、可执行的错误。
